# migrate — repairing a broken chain

The invariant in `./SKILL.md` is what a whole chain must satisfy; a repair is one step toward it, not a licence to edit boundaries by hand. `uv run --locked -m scripts.clopen verify` prints one `journal:month: kind: detail` line per defect and exits 1 while any stands, so its output is the work list and the report.

## The ordering law

Repair the oldest defect first. Every later month's opening was derived from an earlier closing, so regenerating a month while an earlier one is still wrong writes the same error forward. Re-run `uv run --locked -m scripts.clopen verify` over the whole chain after each month, and never batch two months into one change: the difference between two verifier runs is what proves the repair did what it claimed. A month that cannot be read breaks its chain in both directions, so its neighbours are never compared across it and their defects wait until it parses.

## One remedy per defect kind

| kind | what the verifier saw | remedy |
| --- | --- | --- |
| `missing_closing` | a past month has no `closing balances` transaction | `uv run --locked -m scripts.clopen close <that month>`, then re-verify. It writes that month's closing and the next month's opening together, or refuses when the next month already carries an opening, in which case delete that opening first and run it again. Do not expect a stale opening afterwards: either the tool wrote the right one or it wrote nothing. The next defect is the same one a month later — `missing_closing` for the following month, `missing_opening` where a following journal was left without one — because the chain is closed in ascending order, one month per run |
| `missing_opening` | a month has no `opening balances` transaction | an opening is written by the run for the month **before** it: `uv run --locked -m scripts.clopen close <the month before it>`. Naming the month in the defect line closes that month instead and creates the month after it, which is the `unexpected_boundary` write §Future months forbids. When the earlier month still carries its closing, that command refuses, because it would rewrite the pair that closing belongs to: delete both boundaries of the pair, run `uv run --locked -m scripts.clopen close <the month before it>` and say in the report why the pause was forced |
| `opening_mismatch` | an opening does not negate the previous closing, per account and commodity | measure before touching either: `node_modules/.bin/hledger register -I <account> -f ledger/<year>/<year>-<month>/self.journal` over the month of the closing gives the balance the opening has to negate, so the account decides which side is stale. Then delete both boundary transactions of that pair — a hand edit, so report it — and run `uv run --locked -m scripts.clopen close <month of the closing>` to derive them again from one set of balances. The regenerated pair is the confirmation, not the argument: `git diff` shows which side moved, and the side that was already the tool's own output comes back byte-identical. When both sides move, neither was the tool's output, the diff identifies nothing, and the figure from `register` is the only evidence — say in the report that both boundaries were rewritten |
| `closing_not_zero` | a closing posting has no assertion, asserts something other than zero, or does not negate the month's balance | find the account with `node_modules/.bin/hledger register -I <account> -f ledger/<year>/<year>-<month>/self.journal` and compare it with the posting. Regenerate the pair rather than correcting the figure, and never weaken the assertion to match it |
| `closing_incomplete` | an account in scope carries a non-zero balance and the closing has no posting for it | regenerate the pair. A posting added by hand repairs the account and leaves the next opening short of it, which is the same defect a month later |
| `unexpected_boundary` | a month after the current month carries a boundary | delete that transaction, and stop: a boundary there means the tool ran for the month in progress. Never create a month to hold it |
| `unreadable` | hledger could not read the journal, or the month directory is not a calendar month | fix the parse error first (`../fix-journals/SKILL.md`), then re-verify; the directory name is not the diagnosis if the file also fails to parse |
| `boundary_unordered` | a boundary is not the month's first or last transaction, or its date, `time:` tag, or count is wrong | correct the date and the position only: opening on the month's first day and first in the file, closing on its last day and last in the file, `time:` `00:00:00` and `23:59:59` respectively. Two boundaries of one kind mean one is stale — compare both with the previous journal in the family before deleting either |

Regenerating always means the same three moves: delete the affected boundary transactions, `uv run --locked -m scripts.clopen close <month of the closing>`, `bun run format:journal`. Deleting a transaction is a hand edit even when the tool then rewrites it, so the record of it is `git diff` against HEAD: every journal is tracked and the prerequisites require a clean tree, so a committed boundary has a baseline and its removal shows up there. A boundary that was never committed has none, which is one reason for the clean tree — if the tree is not clean, quote the block in the report before deleting it.

## Escalation

Stop and report when the month just repaired still reports the defect it was repaired for, or when two consecutive verifier runs disagree about that month's pair. A defect that appears in a **later** month is not a regression: re-deriving a closing changes the next opening, and with it that month's balances, so `closing_not_zero` and `closing_incomplete` there — and `opening_mismatch` past it — are the expected ripple of a correct repair, repaired in the same ascending pass, one month at a time. A second attempt at the same command is not a diagnosis, and a chain that changes class at or before the repaired month is a question for the owner.

## Hand-off

A journal that does not parse, or an assertion inside a transaction that is not a boundary, is `../fix-journals/SKILL.md`'s job; a chain that parses but does not close is this skill's, and an assertion on a closing posting is this skill's too, because it is repaired by regenerating the pair (`closing_not_zero`). `bun run check` failing on an account, payee, tag, or commodity is never a boundary defect, and no repair here changes one.
